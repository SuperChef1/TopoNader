# NoReflector / NoProposer：前96轮阶段检查

检查日期：2026-10-28。本报告固定截取读取时已经完成的前96轮，不代表实验最终结果。未改变正在运行的实验、代码、载荷、配置或数据，也未追加训练/LLM/FE调用。

## 结论

这组在相同96轮预算下确实表现较好，并非仅仅拿不同轮数比较造成的错觉。最好真实 FE 记录为1.101225，比完整 Bv2 seed42 同期1.042831高5.60%；过程 best-so-far 均值高1.71%。但它并不是“没有 LLM”的实验：121次调用全部来自 Modifier，仍在做基于数据的架构规划与实现。

最具体的轨迹证据是：第68轮继承 BatchNorm 变体，第74轮探索分支找到更好结构，第75轮局部利用分支继续提高，之后多个 FE 结果稳定出现在1.10附近。这与“找到较有利的架构/搜索区域，然后局部搜索跟进”的解释一致，但不能从单条轨迹证明 BatchNorm 或移除两个角色是因果原因。

当前结果使“Reflector 和独立 Proposer 在这个项目里一定有净收益”这一假设受到挑战。它仍不等于已经证明两个角色无用；需要完成统一250轮，并分别看只关 Reflector、只关 Proposer 两组。

## 预算与配置核对

- 前96轮每组新增 FE 尝试1920次，均从相同300初始样本开始，总 FE 样本预算2220。
- NoRNoP 初始文件 SHA256 与 Bv2 相同：`2a5ce46e786cf74fe492b32cad34593457e0f32c98f02a60eef038a09fb98d4f`。
- 运行快照相对 Bv2 seed42 只差实验名，以及 reflector_enabled=false、proposer_enabled=false；Bv2 的缺省角色开关按 true 解释。训练/搜索/覆盖率/继承保护参数未改变。
- 原始数据、COMSOL文件及 MATLAB 主入口/FE入口的当前哈希与 Bv2 起跑前记录一致；这不能排除运行中暂时改动后恢复，也不是对历史 FE 的重新仿真。
- 逐轮 FE 请求输入与 FE 输出在最终累计数据中的追加位置匹配，manifest 输入样本数连续，未发现断链；前300初始样本精确保留，累计数据最大值与记录一致。
- NoRNoP 前96轮1920次 FE 均有效，累计2220个有效样本；完整 Bv2 seed42 同期有1个失败，累计2219个有效样本。比较按尝试预算，而非只按成功次数。
- 13次审查 trace 全部标为两个角色关闭、modifier_joint_proposal；未发现 Reflector / Proposer 调用记录，post_reflection 全部为空。继承4次，回退5次，没有不同临时赢家4次。

## 高值是怎样出现的

成功继承的修改非常局部：

| 轮数 | 实际继承的变化 |
|---|---|
| 27 | predictor_activation：leaky_relu → gelu |
| 56 | predictor_activation：gelu → silu |
| 63 | dropout：0.10 → 0.15 |
| 68 | normalization：layer_norm → batch_norm |

编码器宽度仍为[1024,512,256]，latent_dim=12，Transformer预测器深度2、宽度128、4头。第68轮不是大幅扩容，主要改变编码器的归一化。

第68轮同批 FE 指标：父/子 pairwise 为0.77895 / 0.82632，改善0.04737；父/子 RMSE 为0.32204 / 0.24045；top-k regret 为0.00812 / 0.01861，增加0.01048，在保护门槛0.02以内。因此替换符合现有规则，并非绕过保护。

随后：

- 第74轮最好值从1.028235提高到1.059375，来自 exploration，请求覆盖率0.299027。
- 第75轮从1.059375提高到1.093140，来自 exploitation，请求覆盖率0.295699。
- 第87轮首次超过1.10，达到1.100387。
- 前96轮累计最高5个 FE 值为1.100946、1.100954、1.101106、1.101169、1.101225。高值并非只出现一次，也不是把代理模型预测当成 FE 结果。

这提供了“探索找到好区域、局部利用继续提高”的直接来源证据。第68轮之后仍有重新训练和其他审查轮的临时候选参与搜索，不能把所有后续提高只归给这一处 BatchNorm 修改。MC dropout 推理代码先 model.eval()，仅重新启用 nn.Dropout；静态检查未见为启用 dropout 而把 BatchNorm 也切换为训练模式的操作。

## 为什么去掉两个角色仍可能很好

**事实：去掉的是显式角色，不是这些任务和信息。**当前关闭 Reflector 时，原始指标和历史经历直接进入后续上下文；关闭 Proposer 时，Modifier 一次输出 proposal 与 architecture。Modifier 仍能自行诊断、规划、解释，并实现改变。所以这实际上是单个核心 LLM 角色与分阶段协作的对照，不是有 LLM 与无 LLM 的对照。

**有待验证的解释：**完整流程先把数据压缩成诊断，再变成提案，最后交给 Modifier，可能有信息筛选偏差或传递损失；直接给 Modifier 原始记录可能更有利。单次提出并实现也可能减少“提案和实现不一致”的摩擦。反过来，直接上下文更长也可能增加噪声；单条好轨迹不足以确定净效应。

**另一个替代解释：**在相同42种子下，LLM候选、模型结构、审查时间和累计数据不同，闭环轨迹就会分叉。当前四次局部架构变化与某次全局探索发现可能恰好组合得好。架构搜索不是角色越多必然越强，也不能因为结果不符合预期而判为代码错误。

因此，目前不能拆分“去掉 Reflector”“去掉独立 Proposer”“两者交互”“Modifier获得原始上下文”和随机轨迹各自的贡献。前两种单独关闭实验尚无可比较的运行结果。

## 调用更少不等于成本一定更低

| 前96轮记录 | NoRNoP | 完整 Bv2 seed42 |
|---|---:|---:|
| LLM调用 | 121（全为Modifier） | 151 |
| 输入token | 1,371,570 | 1,037,931 |
| 输出token | 64,779 | 111,902 |

NoRNoP 调用减少，但输入token反而多32.14%，与直接输入原始历史上下文的实现相容。不能仅按角色数或调用次数断言费用更低；需要结合实际输入/输出/缓存价格和训练/FE成本。记录未必覆盖未落盘的失败请求，也不是账单。

## 建议

保持当前代码和门槛，继续到统一250轮，保留这个有利于简化流程的结果；不要为维护多智能体叙事而改变它。随后比较两个单独关闭组，才能判断是否有某一个角色有帮助，另一个角色抵消收益。若简化路线最终在共同种子下持续领先，合理的结论应是保留有效的自适应架构搜索，精简不必要的角色，而非强行证明所有角色都有用。

复查数据见 `evidence.json`（六组统一前96轮）及 `role_checks.json`（调用、继承和高值记录）。
